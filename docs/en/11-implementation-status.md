# MCOS Implementation Status

> **Status:** Living document  
> **Last Updated:** 2026-08-25  
> **Audience:** Contributors and evaluators who need to know **what is spec-only vs. what still needs to be built**.

MCOS has shipped the **P1 MVP and all P2 exit criteria** ([10 §5.6.1](./10-roadmap.md)): the Command Protocol, Runtime, Plugin SDK, and shell are implemented in Kotlin across `mcos-sdk`, `mcos-runtime`, `mcos-android` and four plugins, with the multi-turn Agent loop (2026-08-24) and event-triggered recipes (2026-08-25) closing the checklist. The tables below mark each subsystem **implemented / partial / not started**, citing the commits that landed the code. Rows that remain spec-only are the remaining work.

---

## 0. Golden Rule

> **The docs are the spec. Implementation is aligned to the docs — not the other way around.**
>
> When an implementation and a doc disagree, the doc is correct by default (unless the doc itself is internally contradictory). Do not "fix" a doc to match an implementation. Instead, file the gap here and implement toward the doc.

## 2. Target Module Topology

These are the modules the implementation will introduce, in dependency order. See [`REPOSITORIES.md`](./REPOSITORIES.md) for the full reference card.

**P1 first-party modules** (6 — defined in [REPOSITORIES.md](./REPOSITORIES.md) §2):

| Module | Role | Target phase |
|--------|------|--------------|
| `mcos-sdk` | Plugin contracts (`McosPlugin`, `CommandHandler`, `CommandDescriptor`, …) | P1 (leaf) |
| `mcos-runtime` | Parser → IR, Registry, Permission Kernel, Scheduler, Executor, Audit | P1 |
| `mcos-android` | Jetpack Compose client shell (CLI / Chat) | P1 |
| `plugins:mcos-plugin-hello` | Reference sample plugin | P1 |
| `plugins:mcos-plugin-system` | `sys.notify`, `sys.share`, `sys.clipboard`, `sys.openUrl`, `sys.intent.start`, `sys.vibrate`, the six `sys.device.*` commands (battery/wifi/screen/volume/location/brightness, per the 04 §17 single source of truth) | P1 |
| `plugins:mcos-plugin-camera` | `camera.capture`, `camera.scan` | P1 |

**Planned modules** (later phases — defined in [REPOSITORIES.md](./REPOSITORIES.md) §3):

| Module | Role | Target phase |
|--------|------|--------------|
| `mcos-plugin-files` | `file.*`, `photo.search`, `photo.compress` | P1 |
| `mcos-plugin-iot` | `home.*`, `iot.*` (Home Assistant / Tuya / Matter) | P2 |
| `mcos-plugin-mcp` | MCP client adapter → `mcp.*` | ✅ P2 spike (item 30) + P3 secrets/reconnect/gating (item 31) + enablement (item 32) / 🟡 P3 isolation |

`mcos-server` is no longer a planned module — it shipped as `mcos-server/` (see §3 Memory row) covering the P3 "sync" responsibility, and the marketplace index **client** shipped as `mcos-marketplace/` (in-app search/install wired in `mcos-android`); index hosting and remote policy distribution remain P3 leftovers.

36. ✅ **Process isolation — dispatch seam + trust-level routing (08 §7.2/§8.1, slice 1 of 3)** — the first, pure-JVM slice of process isolation: the runtime now *decides* where each command runs by trust level and routes accordingly, with the actual Binder boundary deferred to the Android slice. **Policy (pure):** `executor/IsolationPolicy.modeFor(trustLevel)` — `BUILTIN` → `IsolationMode.IN_PROCESS` (ships with the runtime, shares the platform key), every other level → `ISOLATED` (an adversarial in-process plugin could otherwise read the grant cache / `AuthStamp` signing key, 08 §7.2 / §5.2 MVP-limitation note); `UNTRUSTED` never reaches dispatch (`CommandRegistry.register` refuses it). **Seam:** `executor/IsolationHost` (mirrors the `WakeScheduler` pattern — pure interface in runtime-core, Android impl injected, graceful fallback) + `IsolatedInvocation` — a fully-marshalable request carrying **only** identity (pluginId/version/commandId) + validated args + the run-bound signed `AuthStamp` + runId/deadline/source; it deliberately carries **no** `HostServices` and no handler ref (in the isolated model the plugin process gets a Binder-stub facade proxy while the main process keeps the real facade, 08 §8.1). **Executor routing:** `invokeHandler` selects `IsolationPolicy.modeFor(entry.trustLevel)` (the trust level rode in `RegistryEntry` since item 24 but was unused at dispatch) — `IN_PROCESS` builds the full `ExecutionContext` (per-plugin secret-resolving + namespaced-sandbox facade) and calls the handler directly; `ISOLATED` with an `isolationHost` wired hands off `IsolatedInvocation` (the in-process handler is never called); `ISOLATED` with no host wired degrades to a **best-effort in-process** invocation (the documented MVP posture) and audits `plugin.isolation_fallback` once per plugin (deduped `SECURITY` record, mirroring `plugin.quarantined`) so the weaker boundary is visible without flooding the trail. ## 7. SDK API Target (spec contract)

The full plugin contract is specified in [04-plugin-sdk.md](./04-plugin-sdk.md) §5–6. The implementation provides all of the following (all four plugins compile against it):

- `McosPlugin` — `id`, `version`, `commands()`, `handler(commandId)`, plus lifecycle (`onLoad`/`onUnload`) per spec.
- `CommandDescriptor` — all spec fields including `permissions`, `inputSchema`, `outputSchema`, `sideEffectClass`.
- `CommandResult` — `Ok(value, artifacts)` and `Err(code, message, retryable, details)` where `details: JsonObject` carries per-error-code structured context ([04 §5.2](./04-plugin-sdk.md), [02 §8.3](./02-command-protocol.md)).
- `McosException` — the plugin-declared error channel for recoverable failures distinct from `CommandResult.Err` ([04 §9.5](./04-plugin-sdk.md)).
- `ExecutionContext` — `runId`, `commandId`, `args`, `stepId`, `auth`, `deadline`, `progress`, `services`.
- `HostServices` facades: `files`, `net`, `ui`, `secureStore`, `clock`, `json`, `memory` — the unified plugin-facing facade ([04 §6](./04-plugin-sdk.md), [01 §11.1](./01-architecture.md)). The historical `PluginHost` name is retired.

See [04-plugin-sdk.md](./04-plugin-sdk.md) §5 for the authoritative Kotlin IDL.
